## Lessons this project paid for — apply all of them

**Trust raw bytes over Ghidra.** Its extents have been wrong more than
sixteen times: it drops trailing literal-pool words, swallows separately
linked sibling functions (a "320-byte" function once concealed a distinct
256-byte one), omits whole functions from its listing, and drops arguments
from its C. Confirm the true extent yourself by finding where the next
function starts. Treat the size above as a hint, not a fact.

**A tiny function is usually NOT a veneer.** Several 4- and 8-byte ones were
each a lone `bx lr` (`0xe12fff1e`) — an empty C++ destructor. A real veneer
is `0xe51ff004` (`ldr pc,[pc,#-4]`) plus a target word, or a plain
`b <target>`. Decode the actual words before hunting for a body. If it IS an
empty destructor: check whether r0 passes through into a caller's
`operator delete` (then the port must return `this`, not void), and whether
the address appears in any DATA word, which tells you if it is dispatched
virtually.

**Verify the call count yourself** by decoding every B/BL word in osos.dec.
Note the split between plain `bl` and predicated forms (`blne`, `bleq`): a
high predicated count usually means the callee has no NULL guard and callers
check it themselves, or that calls are gated on a flag. That is a real
behavioural fact — document and test it.

**The IRAM mirror.** `0x22000000` is NOT mask ROM (that is `0x20000000`). The
relocator at `0x080046e0` copies `0xaed8` bytes from `0x08000000` to
`0x22000000`, so `0x2200XXXX` mirrors osos `0x0800XXXX` and you CAN read the
body of an apparent IRAM target.

**Never invent a callee identity.** If a pointer does not decode as a real
function entry, say so and document the anomaly rather than inventing a
target.

## Procedure

1. Decode the function from raw bytes and work out what it does.
2. Port it into the right module under `src/`, named for what it DOES —
   never `FUN_xxxx`, `param_1`, `uVar`. Register any new module in its parent
   `mod.rs` the moment you create it.
3. Doc header MUST cite the load address, size, verified call count, an
   algorithm summary, and any deliberate deviations. **The load address is
   mandatory** — a smoke check fails the build for any `ported` entry whose
   address appears nowhere in `src/`.
4. Host tests proving behaviour on real edge cases.
   `cargo test --target x86_64-unknown-linux-gnu`
5. `cargo build -Z build-std=core --release` must link.
6. `python3 /home/gabe/Programming/ipod-decomp/tools/match.py 0x082991a4 <symbol>`
   — structural review, NOT instruction-exact. Exit code 1 only means a diff
   was printed; that is EXPECTED and is not a failure.
7. Add the `names.yaml` entry: address, ghidra name, name, size, sig, module,
   `status: ported`, renames, and `notes:` as a FOLDED block (`>-`). Never a
   plain scalar — an unquoted `:` or ` #` from ARM asm breaks the YAML and the
   commit will be refused.
8. Commit on your branch. The pre-commit hook runs the full suite and refuses
   a red tree. That is the gate: never set `RUSTYPOD_SKIP_TEST_GATE=1`.

## Traps that have cost real time

- Struct pointer fields are 4 bytes apart on the 32-bit target but 8 on this
  host. Use `#[repr(C)]` named fields or word indices — NEVER literal byte
  offsets, or two fields silently overlap into one.
- Export gating: `#[cfg_attr(target_os = "none", no_mangle)]`, never a bare
  `#[no_mangle]` (it shadows host libc/libm in test builds).
- `#[inline(never)]` on small exported functions, or LLVM inlines them and
  they stop being real `bl` targets on device.
- LLVM FOLDS byte-identical bodies onto one symbol. If your function could
  compile identically to another, give it its own `link_section`. If it gets
  folded anyway, that is not a defect — verify the symbol still resolves in
  the archive and record the fold in `names.yaml`.
- A veneer whose target LLVM recognises (memcpy/memset/strlen) must load the
  callee through `read_volatile`, or LLVM swaps in a builtin and the veneer
  stops reaching the port entirely.
- Host fixtures backing objects with u32 pointer fields must use
  `crate::testing::try_map_u32_slab` with a NEW UNIQUE constant added to
  `crate::testing::hints`. Never reuse a hint, even within your own module:
  the mapper never unmaps, so a second user lands above 4 GiB and its tests
  skip SILENTLY on every host. This has happened four times.
- Guard-page tests must take the page size from `getpagesize()`.
- Never shadow an existing mutex guard with a second `let _guard = lock()` in
  one test — instant self-deadlock.
- If a fixture is dereferenced by a real (no longer stubbed) callee, make sure
  the fake object is actually big enough to contain what it claims to hold.
- Prefer ALIGNED reads over `read_unaligned` for word-aligned fields: the
  unaligned idiom emits four `ldrb` per word on ARMv5TE. It is a
  pessimization, not a requirement — unless the data really is unaligned.
- **Never run `cargo fmt`.** The crate is not rustfmt-clean; it reformats 339
  files and buries your change.
- Do not mention Claude or AI authorship in commit messages.

## If you cannot port it

If the function depends on the undecrypted zero region
`0x083ee1c1-0x083f25ec`, or is too entangled to port faithfully, do NOT
guess. Record it in `names.yaml` as `status: identified` with notes
explaining exactly what blocks it, commit that, and stop. A well-documented
deferral is a real result; a fabricated port is worse than nothing.
